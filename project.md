## Cloud Worker LLM

- All topic-safety providers use Koog's `LLMClient` and the shared structured JSON response schema. The JVM LiteRT adapter maps Koog's standard JSON schema to LiteRT-LM `ResponseFormat.json`, enabling native constrained decoding rather than maintaining a separate `SAFE`/`UNSAFE` text protocol.
- LiteRT-LM structured output requires `ConversationConfig.enableResponseFormat` and a per-request `ResponseFormat`; these APIs are available in `litertlm-jvm` 0.16.1 and were absent from 0.14.0.
- The JVM LiteRT adapter initializes `Backend.GPU` first and falls back to a new `Backend.CPU` engine when GPU initialization fails; the selected backend and fallback failure are logged with Napier.
- LiteRT-LM 0.16.1 rejects `Engine.close()` before a failed engine has initialized, so GPU initialization failures must be discarded without closing that engine before creating the CPU fallback. `LlmConfig.cachePath` selects a writable LiteRT cache directory; old configurations fall back to a model-specific directory under the JVM temporary directory. Prepare the cache before selecting GPU or CPU so filesystem failures retain their real cause.
- On Windows, LiteRT-LM's Direct3D 12 WebGPU backend requires 64-bit `dxil.dll` and `dxcompiler.dll` from DirectX Shader Compiler to be available beside the worker's Java executable (or already loaded in the process). Without them, GPU initialization fails and the adapter falls back to CPU.

## Backend Core Serialization

- `backend/core` currently declares no kotlinx.serialization `@Serializable` types in its main or test sources. `WrapCacheService` uses the serialization runtime (`Json` and `KClass.serializer()`) to obtain serializers for types defined by other modules. ## Gradle Version Catalog

- Versions in `gradle/libs.versions.toml` that are consumed directly by build scripts rather than a library or plugin `version.ref` must include `# @keep this version`, so catalog cleanup does not remove them. Current examples are Android SDK levels and `jdk`.
- Detekt 2.x uses the `dev.detekt` Gradle plugin and Maven group. Its Ktlint wrapper is `dev.detekt:detekt-rules-ktlint-wrapper`; Gradle reports are `checkstyle`, `html`, `sarif`, and `markdown` (the former `txt` report is removed).
- The repository does not use Detekt baseline files or configure baseline paths on Detekt tasks. Auto-correct is enabled, and every active finding must be fixed in source rather than hidden by a baseline or suppression.
- Detekt 2.0.0-alpha.6 can report false compiler errors when it flattens a KMP test hierarchy containing `expect` declarations in `headlessTest` and matching `actual` declarations in platform test source sets. Confirm these warnings against the corresponding Gradle compilation and test tasks; do not disable rules or add suppressions for this Detekt type-resolution limitation.
- Detekt keeps `NamedArguments` disabled because many Java and third-party APIs cannot use Kotlin named arguments, keeps the duplicate core `MaxLineLength` rule disabled in favor of ktlint's line-length rule, and disables raw-string indentation because whitespace is payload data in Markdown, SQL, PEM, and test fixtures. Package-name checks are disabled because the established `com.storyteller_f` namespace intentionally contains an underscore.
- Detekt's undocumented-public rules and library-public-API rules are disabled because the monorepo mixes Android/framework entry points, Compose UI, endpoint DSLs, protocol data carriers, and cross-module services. Those rules cannot distinguish required public declarations and otherwise encourage boilerplate KDoc or invalid visibility changes. Generated Material Symbols are excluded only from Ktlint property/backing-property naming because their names mirror the upstream icon API.
- Detekt also leaves `MagicNumber`, `MultilineLambdaItParameter`, `BooleanPropertyNaming`, and `TooManyFunctions` disabled: their findings conflict respectively with numeric-domain algorithms and palettes, idiomatic Kotlin/Compose lambdas, stable UI/protocol field names, and declarative feature/driver interface organization. Method-level complexity, cancellation, exception, and null-safety checks remain enabled.
- Detekt leaves `ComplexInterface`, `LabeledExpression`, and `DataClassContainsFunctions` disabled. Complete database/navigation/storage/driver contracts are cohesive boundaries, labeled local returns are required by Kotlin DSL and inline-transform control flow, and behavior on immutable value objects is compatible with the project's explicit `data class` preference.
- `NoNameShadowing` is disabled because nested Compose, collection, test, and route DSL lambdas routinely reuse implicit `it` or short paging parameters in independent scopes; the rule reports those idioms rather than ambiguous access.
- `ElseCaseInsteadOfExhaustiveWhen` is disabled because many mappings intentionally group all unrelated enum/sealed variants into one default, while external sealed hierarchies need a forward-compatible fallback. Exhaustive state machines may still enumerate their cases explicitly.
- `TooGenericExceptionCaught` is disabled for deliberate Result-producing service boundaries, CLI error handlers, and Appium cleanup. `SuspendFunSwallowedCancellation` remains enabled, and broad suspending catches must rethrow cancellation first.
- Ktlint wildcard imports remain forbidden for project packages. Import-on-demand is allowed only for extension-heavy upstream DSL namespaces such as Compose, Ktor, Exposed, coroutines, MinIO, and JMH, where enumerating every DSL symbol obscures the code.
- Detekt library-rule exceptions are file-scoped for required cross-module boundaries: the API endpoint DSL may infer its generated endpoint types, while `backend/core` database helpers and `client/composeCore` global dialog/task/media helpers must remain public for their consuming modules. Module-internal implementations should still be `internal` or `private`.

## Uploads (files)

- API type: Ktor HTTP routes. Endpoint definitions live in `CustomApi` in the `api` module.
- Non-chunked upload: `POST files/upload` (multipart). The server first writes to a local temporary file and validates the request `sha256`; it then uploads to object storage, confirms the returned object name, and stores `FileRecord.sha256` from the request parameter.
- Chunked upload: `POST files/chunk/init` -> `POST files/chunk/{id}/{index}/upload?hash=...` (per-chunk sha256 validation) -> `POST files/chunk/{id}/complete` (object storage compose merge, then write `FileRecord` and clean up chunks).
- Storage implementation: all upload paths go through `ObjectStorageService`.
  - `MEDIA_SERVICE=minio`: MinIO/S3-compatible object storage, with compose support. Presigned reads set `response-content-type` from `FileRecord` for every file without modifying object metadata.
  - `MEDIA_SERVICE=filesystem`: manage objects through filesystem RPC and return direct filesystem HTTP download URLs.

## Resource Management

- When creating an `InputStream`/`OutputStream` and passing it to a consuming function, callers should close it explicitly with `use {}`. For example, when computing `sha256`, use `inputStream().buffered().use { input -> sha256(input.asSource().buffered()) }`.
- Utility functions that receive caller-created streams should not close them internally. The caller should wrap the function call in `use {}` when creating the stream.
- Shared `Result` transformation extensions never retain `CancellationException` as `Result.failure`: they rethrow cancellation received from the source result, thrown by a transformation block, or returned inside a nested result.

## Panel / Worker

- Worker execution records are stored in the backend `TaskRecords` table, with exactly one row per processed business object. The record type is `TaskRecordType`; `objectId` identifies that object, `isSuccess` records the outcome, failures retain a stable string classification plus a safe reason, and failed rows can set `isRetryRequested` for a later worker run. The physical Exposed columns are `object_id`, `is_success`, `failure_type`, `failure_reason`, and `is_retry_requested`.
- Backend `TaskRecord` maps directly to Exposed rows without wrapping the serialized `TaskRecordInfo` DTO. Aggregate counts use the separate `TaskRecordSummary` model rather than synthetic task records.
- Worker schedulers fetch a bounded page of top-level business objects and execute them sequentially. Every object gets its own success or failure `TaskRecord`; a recorded object failure does not prevent later objects in that page from running. Each task type consumes its own administrator-requested retries before fetching new objects. Subscription delivery stops the page at the first incomplete topic: it drains every subscriber page for that topic, writes a durable `SubscriptionSentLog` after each successful subscriber send (keyed by the topic ID), and creates the topic's `TaskRecord` only after an empty subscriber page confirms completion. A later invocation therefore resumes after the last logged subscription when delivery was interrupted.
- Notification-room Aids use the user's Aid when it is non-blank and otherwise fall back to the user ID. Using `null_notification` or `_notification` for users without an Aid violates the globally unique Aid constraint when a worker handles more than one such user.
- Worker topic moderation supports persisted Koog provider settings, the official Koog OpenRouter client, and local LiteRT-LM models. OpenRouter requires an API key and explicit model identifier, always uses the official endpoint, and ignores `baseUrl`. LiteRT requires the configured `modelPath`; the engine is initialized lazily only after the persisted moderation task is enabled.
- Topic moderation retries reviewer initialization on later polling iterations when LLM configuration is not yet present or initialization fails. Configured LLM model IDs are passed through unchanged; Koog requests carry `LlmConfig.temperature` and `maxTokens` through `LLMParams`, including the custom OpenAI-compatible client. Topic content is treated as untrusted prompt data and XML-escaped so it cannot close the prompt boundary.
- Koog topic moderation requests a strict JSON-schema response containing the boolean `is_harmful`; malformed or free-form classifier output is recorded as a model-response failure and diagnosed as invalid structured JSON. The custom OpenAI-compatible client forwards Koog JSON schemas through the OpenAI `response_format` field.
- Worker task runtime settings are persisted in `task_configs`, keyed by `TaskRecordType`, with an enabled switch, fetch size, and wait duration. Missing rows are not synthesized by the database/API and do not run in the worker. The worker reloads each row before every iteration; disabled or missing rows poll every 10 seconds. `taskConfig` presets initialize or upsert rows, and the Panel exposes authenticated list/update endpoints and an editor page. Moderation is controlled by this persisted task configuration without a separate environment override.
- Generic backend settings are persisted in `backend_configs` as a string `key` and `value`. The owning boundary serializes typed values; the CLI writes `LlmConfig` as JSON under `LlmConfig.CONFIG_KEY`, and the Worker decodes it when creating the reviewer.
- `TaskRecordType.TOPIC_MODERATION` advances through topics by primary key. It reviews unencrypted community and user-space topic trees plus rooms whose `communityId` is non-null, skips private/encrypted rooms, changes an unsafe topic author's status to `UserStatus.READ_ONLY`, and sends the author a notification-room message. ACG awards and their success records commit before the worker sends the notification-room message; a notification delivery failure is logged without making the award retryable.
- Panel queries worker execution records through paginated `/admin/task-records`; it supports filtering by task type, and returns all records when no type is provided.
- Panel REST calls are public `PanelSessionManager` extension functions in `client/core/PanelRequest.kt`; `PanelSessionManager` itself only describes session state and capabilities.
- Panel list/detail routes use Navigation 3's `ListDetailSceneStrategy`: users, communities, rooms, topics, files, and titles render side by side once the post-drawer content width reaches 840dp and fall back to the existing single-pane navigation when it is narrower. The list pane has a 420dp preferred width. Public and private room lists share the room detail scene. When the list pane is still the immediate parent, selecting another item replaces the current same-scene detail entry instead of growing the back stack.
- Renovate is configured at the repository root to maintain GitHub Actions, Gradle dependencies, and the Gradle Wrapper. Workflows use the current supported major tags for checkout, JDK setup, Gradle setup, and artifact upload actions.
- App root navigation uses Navigation 3's `ListDetailSceneStrategy`: `HomeScreen` is the list pane, while community, room, topic, and user screens share its detail scene. Content widths of at least 840dp show both panes with a 420dp preferred list width; narrower content stays single-pane. Navigation originating from the Home list replaces its current immediately paired detail; navigation originating from a detail screen pushes a new entry so compact back history is preserved.

## Appium

- Appium and CLI E2E infrastructure plus their lightweight runner modules are always included. Appium test sources live with their independent `androidAppium`, `desktopAppium`, and `wasmAppium` runners instead of application modules because they exercise installed or built artifacts without linking application implementation code. `scripts/test_scripts/build-and-test.sh --e2e` runs Appium and CLI E2E tests without Gradle properties. Docker image builds, distribution preparation, and app installation are dependencies of these explicit E2E tasks, never ordinary `test` / `check`; every Appium `appiumTest` task disables Gradle up-to-date reuse so an explicit E2E run always drives its target. The script uses any booted device in `adb devices` (phone or emulator), only attempting the VMware host emulator when no device is connected. It deliberately does not manage the device-side Appium lock; callers that share an Android device must acquire and lease the lock around the complete `--e2e` invocation.
- `app/androidApp` and `panel/androidApp` can use Robolectric to cover part of the Appium setup and launch flow. For example, writing a session JSON with the same format to `filesDir/appium-session/session.json` and calling `restoreFromStorage` can verify the non-device part of restoring login state from an injected private session.
- The AsciiDoc preview Appium scenario uses a standard `asciidoc` code fence. Android and Desktop verify that the generated preview opens inside the app instead of launching an external browser.
- Appium tests combine target helpers (`AppAppiumHelper` or `PanelAppiumHelper`) with platform helpers (`AndroidAppiumHelper` or `DesktopAppiumHelper`). Target helpers provide package/runtime configuration and create the appropriate session manager; platform helpers own app launch, session injection, cleanup, diagnostics, and driver wrapping. Concrete tests delegate to shared `test*ByHelper` functions.
- Desktop Appium launch scripts are assembled line by line so each shell continuation contains exactly one trailing backslash; two backslashes make Java receive `\` as its main-class argument.
- `Modifier.appiumSemantics` emits transparent HTML overlay nodes only on Wasm; native targets use their ordinary Compose accessibility semantics, and native Appium scenarios locate visible UI text or content descriptions.
- Markdown `object` code fences render only file-backed audio, video, and PDF records. Custom external media types are not recognized and remain visible as highlighted code blocks.
- Markdown `mermaid` code fences render through `mermaidffi-kmp` on Android, JVM, and Wasm, then display the returned SVG through Coil. Rendering runs on `Dispatchers.Default`; failures and unsupported iOS builds fall back to the highlighted source block.
- Mermaid release verification (2026-10-11): Maven Central now publishes 0.0.1-alpha5 (alpha2 and alpha5 appear in the official index); KMP/JVM/Android/Wasm metadata is downloadable. The formal JVM JAR matches its official SHA-256 and contains JNI binaries for Windows x86_64, Linux x86_64, macOS Intel and Apple Silicon. A now resolves alpha5 directly from Maven, without a candidate JAR or validation init script. Earlier 404 results described publication delay and no longer apply. Actual Windows/Linux rendering and Android/Wasm validation results are recorded in the current verification report; binary presence alone does not prove runtime compatibility.
- Markdown inline and block math placeholders use `rememberLatexMeasurer` dimensions. Fixed font-size multipliers clip tall operators such as `\\sum` with upper and lower limits and must not be reintroduced.
- `scripts/test_scripts/build-and-test.sh` only runs device/UI and end-to-end suites. Its `--tests` option accepts multiple filters in one occurrence or across repeated occurrences and passes each safely quoted filter to the selected concrete test tasks. Run ordinary unit suites directly with Gradle.
- Navigation 3 provides `LocalListDetailSceneScope` to list/detail entries only when the adaptive list-detail strategy owns the current multi-pane scene. Detail search bars use that scope to omit their duplicate self avatar in multi-pane layouts while retaining search and compact single-pane actions. UserPage exposes its own-user topic creation as a leading search-bar action; the self avatar's create button always opens the global Compose menu and never derives a creation target from `SearchScope`.
- The local Linux Appium driver retains AT-SPI object paths for click commands across result-order changes. Re-finding only by name loses duplicate-node identity; disappeared targets must be reported stale instead of clicked at cached coordinates.
- Linux AT-SPI nodes can transiently fail individual role/name/text reads while Compose updates the accessibility tree. Element lookup must isolate those property failures instead of abandoning the node's entire subtree. PyAT-SPI can also retain one tree snapshot for a helper process, so element polling starts a fresh helper for each traversal; single-element lookup stops at its first match, and a long empty traversal that crosses the deadline receives one final fresh-process query so newly opened controls such as `close preview` are not missed.
- AndroidX's asynchronous WebWorker SQLite requests can be cancelled after SQLite executes a transaction command but before the driver records the response. The local Wasm worker reconciles `BEGIN`/`END`/`ROLLBACK` with SQLite's autocommit state, while `CancellationSafeSQLiteDriver` drains every already-started worker response before propagating cancellation. Wasm Room remains explicitly configured with a single connection pool.
- `app/wasmAppium` and `panel/wasmAppium` are always available through their explicit `appiumTest` tasks. They serve the built Compose Wasm distributions locally and run Firefox headlessly through WebDriver. Compose/Wasm renders to a canvas and has no browser-visible semantics, so Appium mode (`?appium=true`) uses transparent HTML overlay nodes emitted by `Modifier.appiumSemantics`; passive nodes do not intercept input, while action and text-input nodes call the corresponding Compose callbacks directly. Off-screen nodes are detached so Appium sees one current semantic owner per visible control.
- App preferences use AndroidX DataStore with a small Compose-facing wrapper instead of `ComposePreferences`, whose 1.1.1 Wasm artifact is not binary-compatible with the current Compose runtime. Android and JVM retain their existing `main.preferences_pb` stores; Wasm uses DataStore `WebLocalStorage` without legacy `ComposePreferences` key migration.
- App notifications use `kmpnotifier-local` 2.0.0 across Android, JVM, and Wasm. The app owns a small permission `StateFlow`; platform code initializes KMPNotifier and Android requests runtime permission through `ComponentActivity.permissionUtil()`. - Browser Appium reuses the normal backend topology via `runAppiumTestEnvironment`. ## Gradle Tool Scripts

- The root `compileAllNoRelease` task includes Kotlin/Wasm main compilation tasks by matching the `KotlinWasmJs` task-name suffix. Executable, test, release, benchmark, and JMH compilations remain excluded so verification does not link multiple memory-intensive Wasm binaries in parallel.
- `scripts/build_scripts/gradle-prune-implementations.sh` uses `./gradlew projects` to discover the modules actually included in the current build. It only processes those modules' `build.gradle.kts` files, avoiding accidental dependency removal from modules that are not included.
- The prune check runs `assemble` by default, which can be overridden with `GRADLE_PRUNE_TASK`. Script arguments are forwarded to Gradle, for example `-Pserver.flavor=...`.
- Each candidate `implementation` is verified on top of the cumulative "confirmed removable" state. On failure, only the current candidate is rolled back, preventing final deletion of dependencies that were never validated in combination.
- KMP modules that add custom intermediate source sets generally call `applyDefaultHierarchyTemplate()` after target declarations and before `sourceSets {}`. Examples include `shared`, `client:room`, `client:sqlite-now`, `client:kotbase`, `client:composeCore`, `app:composeApp`, and `panel:composeApp`; custom sets such as `jvmAndroidMain`, `noJvmMain`, or `headlessTest` are then attached with explicit `dependsOn` edges.

## Account 2FA

- User sign-in used to be a single private-key signature step through `/accounts/sign-in`. After TOTP is enabled, that endpoint returns `SignInResponse.RequiresTotp` and marks the Ktor session as `UserSession.TwoFactorPending`; the client then calls `/accounts/sign-in/totp` to complete sign-in.
- User 2FA settings use the protected `CustomApi.Users.TwoFactor` API. Backend data is stored in the `UserTwoFactors` table, and Exposed `MigrationUtils.statementsRequiredForDatabaseMigration` automatically adds the table.
- The TOTP backend implementation lives in `cloud/service`. It uses JDK `SecureRandom`, Base32, and `HmacSHA1` to implement RFC 6238 directly, and generates standard `otpauth://totp/...` URIs for Google Authenticator and similar clients.

## Server Configuration

- User sign-up is controlled by the server environment variable `ENABLE_SIGN_UP`. It defaults to enabled when unset, and only rejects `/accounts/sign-up` when explicitly set to `false`.

## Worker LLM Moderation

- `cloud/worker` sends topic-safety classification through an OpenRouter/OpenAI-compatible chat-completions response schema. OpenRouter failures are JSON objects with an `error` field and no `choices`; the compatible client must validate the HTTP status and decode/report that error before attempting to deserialize the success response, otherwise the useful upstream failure is masked as a missing `ChatCompletionResponse.choices` serialization error.

## Wasm

- Yarn lockfile ownership belongs to the root build: `build.gradle.kts` configures `YarnRootExtension` and `WasmYarnRootExtension` through their respective plugin callbacks. JS uses `kotlin-js-store/yarn.lock`; Wasm uses `kotlin-js-store/wasm/yarn.lock`. App and Panel must not override these root extensions. The current build enables only Wasm targets, so use `kotlinWasmUpgradeYarnLock` to update the active lockfile and `kotlinWasmStoreYarnLock` to check it; the migrated JS lockfile preserves the previous resolutions for when a JS target is enabled again. Keep lockfile mismatch checks enabled.

- Wasm targets are always enabled; `target.wasm` is no longer a project property.
- Browser deployments serve the app and API from different origins. The Wasm Ktor client must configure Fetch with `credentials: include` only for requests whose origin matches the configured API origin; cross-origin media requests keep the browser default and do not send credentials. The API edge must allow credentials for explicit app/panel origins and expose `WWW-Authenticate` so `SingleFlightCustomAuthPlugin` can read the custom authentication challenge. Credentialed CORS must not use a wildcard origin.
- The authenticated WebSocket endpoint is `/ws`; clients and reverse proxies must use this path.
- App and Panel load a bundled Noto Sans SC font into Compose typography on Wasm so Canvas/Skia rendering does not depend on browser CSS font fallback. On secure Chromium contexts with Local Font Access, the `client/composeCore/local-font-access` bridge waits for the first pointer or keyboard interaction, requests permission, and replaces the bundled fallback with the first preferred installed CJK font. Production response headers must allow `local-fonts=(self)` in the Permissions Policy. Firefox and denied/unsupported Local Font Access paths continue using the bundled font.
- The cacheable `downloadNotoWasmFont` task downloads Noto Sans SC Regular and its SIL OFL license from the pinned Noto CJK `Sans2.004` release, verifies both SHA-256 hashes, and exposes them as generated `wasmJsMain` Compose resources. Do not commit the 8.3 MB generated font into source control.
- `:app:webApp` and `:panel:webApp` define the executable `wasmJs` browser targets. `:app:composeApp` and `:panel:composeApp` retain non-executable Wasm targets for shared UI and platform actuals. Shared modules such as `shared`, `api`, `client:core`, `client:model-storage`, `client:room`, `client:bot-lib`, and `client:asciidoc-parser` also define Wasm targets.
